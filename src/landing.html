The question this site exists to answer

Can what a system understands be made queryable, falsifiable and provenance-linked?

That is the V2 question, and it is a different question from the one this page used to ask. Graphonomous began as an MCP memory whose graph changes shape from outcomes; that engine still ships, below, on one platform. Graphonomous V2 is a derived semantic/evidence graph over the registries that already hold the stack’s truth — ComputeDriven, TRVM, the invariant factory, and Super (CD) — read at pinned commits, projected into content-addressed records, sealed as a WallRiderLang world under a profile Graphonomous declares as data, and certified through TRVM. Every id is minted by the kernel that owns it. Nothing in it is a model’s opinion. Whether the graph earns its keep is the open question; what is settled is that it seals, verifies, and can be read.

The direction — Graphonomous V2

A graph of what the stack knows, sealed by the language the stack is written in.

{{V2_DEFINITION}} {{V2_BOUNDARY}} Concretely: an adapter reads a registry at a pinned commit and emits nodes, relations, assertions and source locations; the projector folds them into a content-addressed root; the semantic world is submitted to WallRiderLang as a Semantic IR 2.0 artifact and comes back with a real world id and a kernel-minted id for every relation and every revision; a certificate is minted over the claim and its chain of code identities through TRVM, and a checker that writes nothing re-derives every plane. A second registry is a second adapter. A wider vocabulary is a new profile row, not a new encoding.

{{V2}}

Three claims a reader can hold this section to. Super is read, not integrated with: the snapshot pins Super’s files by blob and the graph can be held to them; there is no runtime coupling in either direction, and the page says so rather than implying one. WRL is the program: the vocabulary lives in WRL’s profile table, WRL refuses by name what the profile does not declare, and the demo on this domain shows the artifact, the seal and the refusals with real bytes — Programming Graphonomous with WRL. Nothing V2 is installable: it lives at v2/ in the repository, beside the v0.4 engine, and the ledger below keeps the two apart.

What ships today — the v0.4 memory engine

One command — on one platform.

The registry has it, the binary downloads, and the server answers on stdio. It is also the honest version: the installer advertises four targets and only one of them has ever been built. If you are on a Mac, this will fail, and it will fail during npm i rather than later.

The gap is not a mystery and it is not hard: npm/scripts/resolve-platform.js maps two platforms by two architectures, and the release workflow has only ever produced one of the four archives. Until the other three exist, the reachable audience for this package is Linux on x86-64. That is the single largest thing standing between this project and someone outside it trying it.

The architecture, in the only shape that matters

Five machines, because tool choice degrades before capability does.

The engine exposes one tool per phase of the loop rather than one tool per capability. Each machine dispatches on an action parameter, so a client sees a short menu of verbs and the long menu lives underneath. The phases are the same five PULSE names every loop in this portfolio declares.

{{LOOP}}

Every action above is read out of the @valid_actions list in its machine module at build time. When a machine gains one, this page gains one; when this page and the modules disagree, the build stops. That is how the previously published table came to be short by two — retrieve/replay and act/store_trace both existed in the code and neither was on the page.
